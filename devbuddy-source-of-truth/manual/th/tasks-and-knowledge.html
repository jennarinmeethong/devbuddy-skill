Task และ knowledge

ประสานงานข้าม repository และควบคุม canonical knowledge ด้วย owner, approval และ evidence

Manual 0.4.5Workspace task

Bootstrap ไม่ใช่ canonical knowledge

Bootstrap อ่าน evidence จาก manifest และ path ต้อง review และขอ Knowledge Impact Approval ก่อน promote เป็น typed entity ทุก entity ต้องมี `project_ids` ที่ไม่ว่าง

Bootstrap สร้างหรือ update เฉพาะ Context.md และ KnowledgeBase.md เท่านั้น ให้เก็บ business context ใน typed business entities และเก็บ decision ใน typed decisions/; BusinessContext.md กับ DecisionLog.md เดิมเป็นเพียงโน้ต legacy ที่ไม่บังคับใช้

สแกน project 
python3 .devbuddy/tools/bootstrap_knowledge.py \
  --devbuddy-root .devbuddy \
  --project-id fe --dry-run

สร้าง workspace task

งานเดียวข้าม FE และ BE 
python3 .devbuddy/tools/task_memory.py init \
  --devbuddy-root .devbuddy \
  --project-id fe --project-id be \
  --task-id checkout-001

Ledger อยู่ใต้ `.devbuddy/tasks/` และใช้ revision sequence เดียว

ใช้ project-qualified scope

Reserve และ validate 
python3 .devbuddy/tools/task_memory.py reserve \
  --devbuddy-root .devbuddy --project-id fe --project-id be \
  --task-id checkout-001 --scope fe:src/checkout \
  --actor developer --expected-revision 0

python3 .devbuddy/tools/task_memory.py check-scope \
  --devbuddy-root .devbuddy --project-id fe --project-id be \
  --task-id checkout-001 --write-scope fe:src/checkout \
  --changed fe:src/checkout/cart.ts

Scope ที่ไม่มี project ID หรือ changed path ที่อยู่นอก project scope จะถูกปฏิเสธ

ขั้นตอน owner commit

  1. Reserve scope ที่ระบุ project
  2. Dispatch specialist ด้วย read paths และ write scope ที่อนุมัติ
  3. ตรวจ changed paths ก่อนรับ JSON slice record
  4. Commit ด้วย parent revision ที่ถูกต้อง
  5. Release reservation และ validate knowledge
BoundarySpecialist ห้ามเขียน `.devbuddy/` โดยตรง แม้ source scope จะได้รับอนุมัติแล้ว

Analysis และ slice record

Read-only analysis 
python3 .devbuddy/tools/task_memory.py analyze \
  --devbuddy-root .devbuddy --project-id fe \
  --task-id checkout-001

Analysis อยู่ใต้ task directory และไม่ถูก promote อัตโนมัติ สร้าง JSON slice record เฉพาะตอนเปลี่ยน role, checkpoint สำคัญ หรือ blocked เท่านั้น JSON slice record ไม่มีเพดานขนาดไฟล์ แต่ให้ส่งเฉพาะ `next_slice` data ที่ slice ถัดไปต้องใช้ โดยอ้าง path/key แทนการคัดลอก log หรือประวัติ

Workflow ของ skill

DevBuddy ทำหน้าที่เป็น control plane: จัดเส้นทางงานและบันทึกการตัดสินใจ แต่ไม่ทำงานแทน specialist ที่เป็นเจ้าของงานนั้น

  1. เริ่มงาน: ผู้ใช้เรียก adapter โดยชัดเจน Orchestrator เลือก profile ของ adapter ที่กำลังใช้งานจาก settings ร่วม จึงไม่ต้องแก้ settings เมื่อสลับ Codex และ Claude
  2. ตรวจความพร้อม: resolve workspace, validate settings, ตรวจ project ที่ register แล้ว และสร้างหรือ resume task ledger หนึ่งชุดพร้อม memory revision ปัจจุบัน
  3. วางแผน: จัดระดับความเสี่ยง, dependency, tool availability, knowledge impact, cost และ approval แล้วสร้าง role graph ที่เล็กที่สุดแต่มีหลักฐานตรวจสอบอิสระได้
  4. อนุมัติและล็อก: เลือก model/effort ที่ได้รับอนุญาตและเพียงพอต่อแต่ละ slice จากนั้น reserve write scope ที่ระบุ project ก่อน specialist ที่เขียนไฟล์เริ่มงาน
  5. Dispatch: ส่ง task package ที่มี objective, role, artefact ที่อนุญาต, read paths/keys, write scope, parent revision, lock, model/effort, timeout และ exit condition
  6. ตรวจผล: ตรวจ changed paths กับ reservation และ validate JSON slice record ที่คืนมา มีเพียง owner ที่ commit canonical knowledge ที่อนุมัติแล้วด้วย revision ที่ถูกต้องได้
  7. ส่งต่อหรือหยุด: dispatch เฉพาะ role ถัดไปที่ dependency พร้อมเท่านั้น ถ้าขาด approval, tool ใช้ไม่ได้, revision เก่า, scope ชนกัน หรือข้อมูลไม่แน่ชัด ให้เป็น blocked หรือ waiting_user พร้อมคำถามที่เจาะจง
  8. ปิดงาน: ต้องมี evidence, independent QA/Security ตามความเสี่ยง, approval, knowledge declaration และ policy compliance ก่อนรายงานผลให้ผู้ใช้เป็นภาษาไทย

Subagent ทำงานอย่างไร

ผู้ทำงานความรับผิดชอบสิ่งที่ห้ามทำ
Orchestrator / ownerเลือก graph, ตรวจ gate, reserve scope, เลือก model/effort, route record และ commit canonical knowledge ที่อนุมัติแล้วทำ implementation แทน specialist หรือแทน specialist ที่ไม่มีอยู่โดยเงียบ ๆ
Specialist subagentทำ role slice เดียวภายในขอบเขตที่กำหนด เก็บ evidence และคืน JSON slice record หนึ่งรายการเมื่อถึง checkpoint สำคัญเขียน .devbuddy/ โดยตรง ขยาย scope สร้าง artefact ที่ไม่อยู่ใน package เปลี่ยน policy หรือเดาข้อมูลที่หายไป

Specialist ได้รับ reference แทน conversation ทั้งหมด โดยอ่านเฉพาะ role workflow, path, key และ policy ที่ task package ระบุ จึงลด context และให้ role ถัดไปอ่านเฉพาะ delta ที่เกี่ยวข้องแทนการคัดลอกประวัติ

การส่งต่อด้วย record

JSON slice record เป็นผลลัพธ์ระหว่าง agent เพียงรูปแบบเดียว ระบุ task, slice, attempt และ parent revision พร้อม status, result, evidence reference, blocker, approval และ next_slice ที่สั้นที่สุด Role ถัดไปอ่านไฟล์หรือ knowledge key ที่อ้างอิง ไม่อ่าน log ที่ถูกคัดลอกมา

  • completed: owner ตรวจ evidence แล้ว route dependency ถัดไป
  • blocked: ระบุสิ่งที่ไม่ทราบ เหตุผลที่สำคัญ สิ่งที่ตรวจแล้ว และคำถามหรือ dependency ที่ต้องการ
  • waiting_user: รอ decision, approval หรือ configuration จากผู้ใช้
  • failed: เก็บ evidence และหยุดหรือ retry เฉพาะภายใน budget ที่ settings กำหนด
วินัยของ contextเก็บ decision ถาวรใน ledger, fact canonical ใน knowledge entity และ log ขนาดใหญ่ในไฟล์ที่อ้าง path ใส่เฉพาะ state ที่ slice ถัดไปต้องใช้ใน next_slice
