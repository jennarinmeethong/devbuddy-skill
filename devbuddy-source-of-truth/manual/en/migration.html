Migration

Move legacy memory safely and upgrade project-local tools without overwriting user changes.

Manual 0.4.5Explicit apply

Migrate the legacy layout

Preview then apply 
python3 <installed-skill>/scripts/init_project_memory.py \
  --devbuddy-root /path/to/.devbuddy \
  --migrate-layout --dry-run

python3 <installed-skill>/scripts/init_project_memory.py \
  --devbuddy-root /path/to/.devbuddy \
  --migrate-layout

The migration moves core files and typed folders into `knowledge-base/`. It leaves `settings.yaml`, `tasks/` and `tools/` as siblings. Destination conflicts stop the operation before changes are made.

Upgrade project-local tools

Preview then apply 
python3 <installed-skill>/scripts/init_project_memory.py \
  --devbuddy-root /path/to/.devbuddy \
  --upgrade-tools --dry-run

python3 <installed-skill>/scripts/init_project_memory.py \
  --devbuddy-root /path/to/.devbuddy \
  --upgrade-tools

The manifest identifies the previous trusted hash. A tool changed by a user is never silently replaced.

Backup and rollback

  1. Commit or copy the dedicated knowledge repository before migration.
  2. Run dry-run and save its output with the change record.
  3. Apply only after destination conflicts are resolved.
  4. Validate settings, knowledge and task paths after the move.
  5. Rollback by restoring the repository commit or backup; do not manually mix old and new layouts.

Compatibility

Legacy flags remain accepted where unambiguous, but new workspaces should use `--devbuddy-root` and repeatable `--project`. Do not run automatic migration during skill startup.

VersioningCommit `.devbuddy/tools/manifest.json` with the workspace so every collaborator can see which runtime version is trusted.
