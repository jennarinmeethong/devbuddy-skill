Workspace

Keep shared knowledge, task coordination and executable tools together while source code remains in its own repositories.

Manual 0.4.5Multi-project

Choose the workspace root

`.devbuddy` is a control directory and does not have to live in an application repository. It can live beside FE/BE repositories or inside a dedicated knowledge Git repository.

workspace/
├── frontend/
├── backend/
└── knowledge-repo/
    └── .devbuddy/
        ├── settings.yaml
        ├── knowledge-base/
        ├── tasks/
        └── tools/

Register multiple projects

Project IDs are stable names used by settings, bootstrap, knowledge metadata and task scopes. Paths resolve relative to the parent directory of `.devbuddy`.

settings.yaml 
workspace:
  projects:
    fe:
      path: ../frontend
    be:
      path: ../backend
memory_root: knowledge-base

The initializer rejects missing paths, duplicate IDs, duplicate resolved paths and any project path inside `.devbuddy`.

What lives where

PathPurpose
.devbuddy/knowledge-base/Shared canonical knowledge and reviewable bootstrap observations.
.devbuddy/tasks/Workspace ledgers, slice records, reservations and analysis.
.devbuddy/tools/Project-local Python runtime copied by the initializer.
.devbuddy/settings.yamlProject registry and orchestration policy.
Source repositoriesFE, BE or other registered source code; specialists write only approved scopes.

Dedicated knowledge repository

Commit `.devbuddy/` to the knowledge repository. Prefer relative source paths so the workspace remains portable after cloning. Use a local override policy outside committed settings when machine-specific absolute paths are unavoidable.

Antivirus rationaleAfter bootstrap, operational Python runs from the workspace location that your scanner already understands. The global skill provides the one-time initializer and template assets.

Shared knowledge naming

Core files and typed folders live below `knowledge-base/`. Every entity has an immutable ID and a non-empty `project_ids` list. A shared API or business rule may list both `fe` and `be`; repository-specific evidence should identify its project ID and relative source path.
