Get started step by step

Follow one step at a time. You can stop after the first prompt; a workspace and presets are additions for when you begin real project work.

Manual 0.4.6No coding required firstPreview before changing files

Step 0: Prepare

  1. Choose just one AI app you already use: Codex, Claude Code, or OpenCode.
  2. Open your computer's Terminal, or ask a project administrator to run the installation if Terminal is unfamiliar.
  3. Have the project folder ready, but do not put passwords or real customer data in the request.
  4. Ask the project administrator for the approved DevBuddy release tag or commit SHA. Replace <approved-ref> below with that value; never use a mutable branch such as main for real work.
No host or installation permission? You can safely stop here. Send this page to an administrator, then continue at step 2 when installation is complete.

Step 1: Choose and install your host

Use only the block for your app. Run every command in Terminal and replace <approved-ref> before pressing Enter. If asked to approve something, first verify the plugin name and source.

Codex 
codex plugin marketplace add jennarinmeethong/devbuddy-skill --ref <approved-ref> --json
codex plugin add devbuddy-codex@devbuddy --json
# Close or start a new Codex task, then type:
$devbuddy Help me plan my first task

OpenCode

OpenCode 
opencode plugin 'github:jennarinmeethong/devbuddy-skill#<approved-ref>::path:plugin/devbuddy-core/opencode' --global
# Keep --global for every project, or remove it for the current project only.

OpenCode uses project agent presets, so complete step 4 before selecting an agent in its UI. If a plugin or agent is not visible after installation, read plugin troubleshooting.

Step 2: Send your first request

A good request needs no AI terminology. State only four things: goal, what exists, constraints, and the result you want. Copy this example and replace the bracketed text.

A safe example prompt 
I want [outcome] for [users or project].
Today we have [related files, system, or information].
The constraints are [time, budget, rules, or forbidden actions].
First, summarise your understanding and ask necessary questions.
Then propose a plan without editing files or using external services.
State the roles needed, why, risks, and every approval point.

Example first task: “I want a login page for an internal web site. It already uses React and must work on mobile. Do not edit files yet. Summarise requirements and propose a plan with the tests we should have.”

Step 3: Choose a preset when you know the work type

A preset is a list of roles DevBuddy should consider. It does not grant new permission, production access, or authority to act without you. You can skip presets while experimenting.

Step 4: Create a workspace for continuing work

Skip this for a one-off question. Use it when several people or agents share one project, work spans repositories, or you need durable task and knowledge history. The first command is a dry run; only the second creates .devbuddy.

Preview workspace creation first 
python3 <installed-plugin-root>/scripts/init_project_memory.py \
  --devbuddy-root /path/to/team-workspace/.devbuddy \
  --project app=/path/to/your-project --dry-run

python3 <installed-plugin-root>/scripts/init_project_memory.py \
  --devbuddy-root /path/to/team-workspace/.devbuddy \
  --project app=/path/to/your-project

<installed-plugin-root> is the folder where the plugin was installed, not your project folder. Ask an administrator for the path rather than guessing. After creation, run python3 .devbuddy/tools/validate_project_settings.py .devbuddy/settings.yaml from the team workspace folder.

Step 5: Read results and approve at the right point

Before allowing work to continue, check five things: whether the goal is correct, which files or systems could be touched, what each role will do, how success will be tested, and where approval is needed. If any is missing, reply: “Explain this in plain language and do not make changes yet.”

When the plan is correct, set a clear boundary, for example: “I approve changes only under src/login and unit tests. Do not deploy or send data outside this computer.”

Step 6: Stop and ask when you see these signals

  • A command will delete files, write to a database, deploy, send data out, or create a cost.
  • You do not know what a role, tool, or command does.
  • The system asks for a secret, API key, or real customer data.
  • The result differs from what you intended.

Reply: “Stop. Explain the impact, alternatives, and rollback in simple language.” Decide only after you have that information.

Stuck?

If the plugin is not visible after installation, read plugin troubleshooting. For workspace concepts, read Workspace. For installation or updates from Git, read Git install. Always read Database profiles before using a database.

What next?

After the first prompt succeeds, choose one small task and have DevBuddy show its plan first. Add a preset or workspace only when it becomes useful; you do not need every capability on day one.
