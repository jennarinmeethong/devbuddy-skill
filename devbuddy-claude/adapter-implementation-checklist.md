## Adapter notes

- Claude Code exposes reasoning effort through the agent-definition `effort` frontmatter field, not as a per-call parameter. The adapter therefore installs one subagent per role and effort tier (9 x 6 = 54) and overrides the model per dispatch, which satisfies `DBY-MODEL-002` without an exception. Agent definitions must not pin a `model`; `scripts/validate_skill_metadata.py` enforces this.
- The shipped Claude effort ladder is `low`, `medium`, `high`, `extra`, `max`, and `ultracode`. The Orchestrator selects the lowest sufficient tier and blocks dispatch if the host cannot run the selected named agent; it must never fall back to a generic agent.
- Invocation is gated by `disable-model-invocation: true` in `SKILL.md`, not by instruction. Every approval gate here assumes the user chose to open a delivery task; if Claude could load the skill on its own it could begin dispatching specialists for a request the user never gated. `scripts/validate_skill_metadata.py` requires the field and rejects a `false` value, and the frontmatter check is covered by `SkillMetadataTests` in `tests/test_project_memory.py`.
- Policy is otherwise enforced through skill instructions only. The adapter does not modify `.claude/settings.json` and installs no hooks, so Claude Code's own permission prompts remain the user's backstop. This is a deliberate, user-approved scope decision recorded in `references/policy.md`.
- Only self-contained scripts are installed (`SKILL_SCRIPTS` in `scripts/install_claude_adapter.py`). The conformance and manual checkers compare this adapter against `devbuddy-source-of-truth/`, which no install contains, so they stay repository-only and `SKILL.md` splits its validation commands along that line.
- The upstream skill-creator quick validator remains unavailable because its optional `PyYAML` dependency is not installed; no package was installed. The adapter validates with `scripts/validate_skill_metadata.py`, a standard-library checker that also verifies all 54 agent definitions.
