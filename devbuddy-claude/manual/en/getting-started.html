Getting started

Install the host Plugin or profile, create a multi-project workspace, validate the local runtime, and start the first bounded task.

Manual 0.4.6Plugin 1.0.1Dry-run first

Prerequisites

Use Python 3.9 or newer for workspace scripts, an authenticated supported host, and filesystem access to the workspace plus every registered repository. Back up and version a dedicated knowledge repository before applying changes.

Install the host package

New installations use one host-native Plugin/profile. Read the Plugin-first guide for lifecycle and empty-list recovery. Do not install devbuddy-core or a standalone skill separately.

Claude Code — from this repository root 
claude plugin validate plugin/devbuddy-claude-code
claude plugin marketplace add . --scope user
claude plugin marketplace list
claude plugin install devbuddy-claude-code@devbuddy --scope user --yes
claude plugin list --json
# in Claude Code
/reload-plugins
/devbuddy-claude-code:devbuddy <task>
Legacy boundaryThe old adapter installers are migration-aware 1.x compatibility shims. They report the Plugin path by default and never remove or overwrite host files.

Initialize the workspace

Choose an approved .devbuddy location. Use the initializer shipped by the installed package/profile; the placeholder below represents that package-owned path. Repeat --project ID=PATH for FE, BE, mobile, services, or other repositories.

Preview, then apply 
python3 <installed-plugin-root>/scripts/init_project_memory.py \
  --devbuddy-root /path/to/knowledge-repo/.devbuddy \
  --project fe=../frontend \
  --project be=../backend \
  --dry-run

python3 <installed-plugin-root>/scripts/init_project_memory.py \
  --devbuddy-root /path/to/knowledge-repo/.devbuddy \
  --project fe=../frontend \
  --project be=../backend

Relative paths resolve from the parent of .devbuddy. Paths must exist, be unique after resolution, and stay outside the workspace control directory.

Configure settings

The initializer creates a versioned project registry, memory locator, and provider-specific model/effort defaults. Narrow the approval boundary before dispatch and keep host selection in the installed profile.

settings.yaml 
schema_version: 1
settings_version: 0.4.6
workspace:
  projects:
    fe:
      path: ../frontend
    be:
      path: ../backend
memory_root: knowledge-base
orchestration:
  max_concurrency: 2
  task_timeout_seconds: 900
  retry_limit: 1
  adapter_profiles: [claude, codex]
  approved_models: [...] # host-specific approved names
  approved_effort_levels: [...] # ranked defaults
tools:
  is_rtk: false

When settings_version differs, preview and run init_project_memory.py --upgrade-settings; it fills only missing defaults. Set tools.is_rtk: true only when RTK is available on PATH; unsupported commands remain direct.

Validate and bootstrap

Project-local tools 
python3 .devbuddy/tools/validate_project_settings.py .devbuddy/settings.yaml
python3 .devbuddy/tools/bootstrap_knowledge.py --devbuddy-root .devbuddy --project-id fe --dry-run
python3 .devbuddy/tools/bootstrap_knowledge.py --devbuddy-root .devbuddy --project-id fe --apply
python3 .devbuddy/tools/validate_knowledge.py --devbuddy-root .devbuddy

Repeat bootstrap for be. Review observations before applying; bootstrap writes only its labelled observation files and never invents typed canonical entities.

Create the first task

Workspace task 
python3 .devbuddy/tools/task_memory.py init \
  --devbuddy-root .devbuddy \
  --project-id fe --project-id be \
  --task-id checkout-001

Use one ledger for cross-repository work. Continue with Tasks & knowledge to reserve project-qualified scopes and route evidence.
