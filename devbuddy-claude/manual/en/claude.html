Claude Code Skill adapter

Status: implemented at common specification 0.1.1. All required checklist items in devbuddy-claude/adapter-implementation-checklist.md are done.

Prerequisites

  • Claude Code installed, authenticated, and supported in the target environment.
  • Subagent support with the effort frontmatter field. The adapter depends on it to express the per-dispatch effort level.
  • Python 3 available, if you want to run the bundled validation scripts. They use only the standard library; no packages are installed.
  • Your explicit approval for any installation, update, paid account, or model usage.

Verify the installation with claude doctor only after you authorise running it. Do not treat a missing tool as installed.

What gets installed

ArtefactDestinationPurpose
Skill (SKILL.md, references/, roles/, templates/, schemas/, scripts/, manual/, settings.yaml)~/.claude/skills/devbuddy/The Orchestrator and its policy references
27 subagent definitions devbuddy-<role>-<effort>.md~/.claude/agents/The 9 specialist roles at low, medium, and high effort

Installing at user level makes DevBuddy available in every project, at the cost of 27 devbuddy-* entries appearing in your agent list. Pass --claude-root to install into a single project's .claude/ instead.

Installation

  1. Confirm every required item in devbuddy-claude/adapter-implementation-checklist.md is done.
  2. Preview the exact file list — dry run is the default, nothing is written: 
    python3 scripts/install_claude_adapter.py
  3. Install once the list looks right: 
    python3 scripts/install_claude_adapter.py --apply
  4. Restart or refresh the Claude Code session so /devbuddy and the devbuddy-* agents load.

The installer refuses to overwrite any existing file it cannot identify as a DevBuddy artefact. A conflict is yours to resolve; the installer will not guess.

Never copy credentials, connection strings, or personal data into Claude settings or prompts.

Configuration

Create <project-root>/.devbuddy/settings.yaml before the first dispatch:

schema_version: 1
memory_root: .devbuddy
orchestration:
  max_concurrency: 2
  task_timeout_seconds: 900
  retry_limit: 1
  approved_models:
    - id: haiku
      rank: 1
      allowed_roles: [developer, qa]
      allowed_risks: [low]
    - id: sonnet
      rank: 2
      allowed_roles: [ba-pm, architect, developer, qa, security, reviewer]
      allowed_risks: [low, medium, high]
  approved_effort_levels:
    - id: low
      rank: 1
      allowed_roles: [developer, qa]
      allowed_risks: [low]
    - id: medium
      rank: 2
      allowed_roles: [ba-pm, architect, developer, qa, security, reviewer]
      allowed_risks: [low, medium, high]

The adapter ships a ranked default of haiku / sonnet / opus and low / medium / high so it is usable immediately. That default is an approval boundary, not a cost waiver — a new provider, a wider allowlist, or a model with different privacy behaviour is a fresh approval decision.

max_concurrency, task_timeout_seconds, and retry_limit have no default on purpose: they commit your time and money, so DevBuddy asks rather than assumes. A missing budget blocks dispatch.

Differences from the Codex adapter

  • Invocation is /devbuddy rather than $devbuddy.
  • The effort level is carried by the selected subagent's effort frontmatter, not by a dispatch parameter. Choosing the tier is choosing the effort.
  • The model is passed per call and overrides frontmatter, so agent definitions deliberately leave model unset.
  • Independent slices are dispatched as several Agent calls in one message, subject to max_concurrency and Claude Code's own concurrent-subagent limit.

Verification

python3 scripts/validate_skill_metadata.py .
python3 scripts/check_adapter_conformance.py
python3 scripts/validate_manual.py manual
python3 scripts/run_scenarios.py tests/scenarios.json
python3 scripts/validate_project_settings.py <project-root>/.devbuddy/settings.yaml
python3 scripts/validate_knowledge.py --project-root <project-root>

The initializer places KnowledgeBase.md, the other core files, typed knowledge, and task ledgers directly under <project-root>/.devbuddy/. For an external vault, validate it with python3 scripts/validate_knowledge.py --root <approved-external-memory-root>.

After installing, confirm that /devbuddy resolves to this skill and that the devbuddy-* agents appear in your agent list. Then run a bare read-only task such as /devbuddy inspect the repository and report the current delivery risks and check that the Orchestrator creates a task ledger, records a model and effort pair with its reason, selects the role graph, and dispatches a real specialist subagent.

If project settings are absent, the run should stop at waiting_user. That is correct behaviour, not a failure.

Upgrading

  1. Change the common specification in devbuddy-source-of-truth first, then synchronise the checklist item.
  2. Regenerate the subagents after any role change: python3 scripts/generate_agents.py. Verify with --check.
  3. Re-run the validators, update both manual languages, then re-run the installer. It replaces its own files in place.

Troubleshooting

SymptomCause and action
/devbuddy is not recognisedThe skill is not installed or the session predates it. Check ~/.claude/skills/devbuddy/SKILL.md, then restart the session.
Another devbuddy skill respondsTwo skills share the name. Remove or rename the other one; DevBuddy will not guess which you meant.
Dispatch stops at waiting_user immediatelyUsually a missing or invalid .devbuddy/settings.yaml. Run validate_project_settings.py and read the reported field.
devbuddy-<role>-<effort> not foundThe agents were not installed, or the effort tier is not permitted for that role and risk. Re-run the installer and check approved_effort_levels.
Effort level cannot be confirmedTreat it as a blocked dispatch. An unverifiable selection is not a completed one.
Validators fail on a Python runtimeConfirm Python 3 is available. Do not install anything without your own decision — the scripts need no packages.

Do not use a permission-bypass mode to work around a DevBuddy approval gate. If the permissions, tool access, or model availability in your environment differ from common policy, mark the affected checklist item incomplete and record a remark rather than working around it.
