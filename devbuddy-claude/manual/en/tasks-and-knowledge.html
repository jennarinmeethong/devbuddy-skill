Tasks and knowledge

Coordinate work across repositories while keeping canonical knowledge owner-controlled, evidence-backed, and independent of the host Plugin cache.

Manual 0.4.6Project-qualified scopesOwner commit

Bootstrap is not canonical knowledge

Bootstrap scans evidence from manifests and paths. Review it, obtain Knowledge Impact Approval, and promote durable facts into typed entities. It writes only labelled observation files and never invents business policy, typed entities, or decisions.

Scan one project 
python3 .devbuddy/tools/bootstrap_knowledge.py \
  --devbuddy-root .devbuddy \
  --project-id fe --dry-run

Create a workspace task

One task across FE and BE 
python3 .devbuddy/tools/task_memory.py init \
  --devbuddy-root .devbuddy \
  --project-id fe --project-id be \
  --task-id checkout-001

The task ledger records one revision sequence below .devbuddy/tasks/. The Plugin routes the host command, but the ledger and knowledge remain workspace state.

Use project-qualified scopes

Reserve and validate 
python3 .devbuddy/tools/task_memory.py reserve \
  --devbuddy-root .devbuddy --project-id fe --project-id be \
  --task-id checkout-001 --scope fe:src/checkout \
  --actor developer --expected-revision 0
python3 .devbuddy/tools/task_memory.py check-scope \
  --devbuddy-root .devbuddy --project-id fe --project-id be \
  --task-id checkout-001 --write-scope fe:src/checkout \
  --changed fe:src/checkout/cart.ts

A scope without a project ID is rejected. A change under be: cannot be accepted under an fe: reservation.

Owner commit protocol

  1. Reserve the project-qualified scope.
  2. Dispatch the specialist with approved read paths, write scope, model, effort, and exit condition.
  3. Validate changed paths and the JSON slice record.
  4. Commit the owner revision with the expected parent revision.
  5. Release the reservation and run knowledge health checks.

Specialists never write .devbuddy/ directly, even when their source scope is approved.

Analysis and slice records

Read-only analysis 
python3 .devbuddy/tools/task_memory.py analyze \
  --devbuddy-root .devbuddy --project-id fe \
  --task-id checkout-001

Create a JSON slice record at a role boundary, material checkpoint, or blocker. Keep next_slice to the state the next slice needs and reference files/keys instead of copying logs.

Workflow across hosts

  1. The user explicitly invokes the installed host Plugin/profile.
  2. The Orchestrator resolves settings, projects, task ledger, risk, approvals, and the smallest useful role graph.
  3. The owner selects an approved model and effort, reserves a write scope, and dispatches a bounded package.
  4. The owner validates evidence and record state, then routes or stops the next dependency.
  5. Missing approval, unavailable tool, stale revision, conflict, or uncertainty becomes blocked or waiting_user.
  6. Closure requires evidence, independent checks where required, approvals, knowledge declarations, and policy compliance.

How specialists work

ActorResponsibilityMust not do
Orchestrator / ownerChoose graph, validate gates, reserve scope, select model/effort, route records, and commit approved canonical knowledge.Do specialist implementation or silently replace a missing specialist.
Specialist subagentPerform one bounded role slice, gather evidence, and return one JSON slice record at a material boundary.Write .devbuddy/, widen scope, create unlisted artifacts, change policy, or guess missing facts.

Record flow

The JSON slice record is the only inter-agent result. It identifies task, slice, attempt, and parent revision; records status, result, evidence references, blockers, approvals, and a minimal next_slice.

  • completed — owner checks evidence and routes the next dependency.
  • blocked — name the unknown, why it matters, what was checked, and the exact question/dependency.
  • waiting_user — wait for a decision, approval, or missing configuration.
  • failed — preserve evidence and stop or retry only within the configured budget.
