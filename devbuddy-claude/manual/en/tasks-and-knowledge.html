Tasks and knowledge

Coordinate work across repositories while keeping canonical knowledge owner-controlled and evidence-backed.

Manual 0.4.6Workspace task

Bootstrap is not canonical knowledge

Bootstrap scans evidence from manifests and paths. Review it, obtain Knowledge Impact Approval, then promote durable facts into typed entities. Every entity includes a non-empty project_ids list.

Only Context.md and KnowledgeBase.md are created or updated by bootstrap. Store business context in typed business entities and decisions in typed decisions/ entities; legacy BusinessContext.md and DecisionLog.md are optional notes.

Scan one project 
python3 .devbuddy/tools/bootstrap_knowledge.py \
  --devbuddy-root .devbuddy \
  --project-id fe --dry-run

Create a workspace task

One task across FE and BE 
python3 .devbuddy/tools/task_memory.py init \
  --devbuddy-root .devbuddy \
  --project-id fe --project-id be \
  --task-id checkout-001

Use one ledger for cross-repository work. It records project IDs and one revision sequence below `.devbuddy/tasks/`.

Use project-qualified scopes

Reserve and validate 
python3 .devbuddy/tools/task_memory.py reserve \
  --devbuddy-root .devbuddy --project-id fe --project-id be \
  --task-id checkout-001 --scope fe:src/checkout \
  --actor developer --expected-revision 0

python3 .devbuddy/tools/task_memory.py check-scope \
  --devbuddy-root .devbuddy --project-id fe --project-id be \
  --task-id checkout-001 --write-scope fe:src/checkout \
  --changed fe:src/checkout/cart.ts

A scope without a project ID is rejected. A change in `be:` cannot be accepted under an `fe:` scope.

Owner commit protocol

  1. Reserve the project-qualified scope.
  2. Dispatch the specialist with only approved read paths and write scope.
  3. Validate changed paths before accepting the JSON slice record.
  4. Commit the owner revision with the expected parent revision.
  5. Release the reservation and run knowledge health checks.
BoundarySpecialists never write `.devbuddy/` directly, even when their source scope is approved.

Analysis and slice records

Read-only analysis 
python3 .devbuddy/tools/task_memory.py analyze \
  --devbuddy-root .devbuddy --project-id fe \
  --task-id checkout-001

Analysis is saved below the task directory and is not promoted automatically. Create a JSON slice record only at a role boundary, material checkpoint, or blocker. JSON slice records have no file-size cap; keep `next_slice` to the data the next slice needs and reference files and keys instead of copying logs or history.

Skill workflow

DevBuddy is a control plane. It routes work and records decisions; it does not replace the specialist who owns the work.

  1. Start: the user explicitly invokes the adapter. The Orchestrator reads the active adapter profile from the shared settings; no setting is changed when switching between Codex and Claude.
  2. Validate: resolve the selected workspace, validate settings, inspect registered projects, and create or resume one task ledger with its current memory revision.
  3. Plan: classify risk, dependencies, tool availability, knowledge impact, cost, and approvals. Build the smallest role graph that can produce independent evidence.
  4. Authorize: choose the lowest permitted model and effort for each ready slice. Reserve a project-qualified write scope before a writing specialist starts.
  5. Dispatch: give the specialist a bounded task package: objective, role, allowed artefacts, read paths/keys, write scope, parent revision, lock, selected model/effort, timeout, and exit condition.
  6. Verify: check changed paths against the reservation and validate the returned JSON slice record. The owner alone commits approved canonical-memory changes with the expected revision.
  7. Route or stop: dispatch only a dependency-ready next role. A missing approval, unavailable tool, stale revision, conflict, or uncertain fact becomes a focused blocked or waiting_user state.
  8. Close: require required evidence, independent quality/security checks for the risk, approvals, knowledge declarations, and policy compliance before reporting completion in Thai.

How specialists work

ActorResponsibilityMust not do
Orchestrator / ownerChoose the graph, validate gates, reserve scopes, select approved model/effort, route records, and commit approved canonical knowledge.Do specialist implementation or silently substitute a missing specialist.
Specialist subagentPerform one bounded role slice, work only in the assigned scope, gather evidence, and return one JSON slice record at a material boundary.Write .devbuddy/ directly, widen scope, create unlisted artefacts, change policy, or guess a missing fact.

A specialist receives references rather than the full conversation. It reads only the role workflow, paths, keys, and policies named in its task package. This keeps context small and lets the next specialist receive the relevant delta instead of a copied history.

Record flow

The JSON slice record is the only inter-agent result. It identifies the task, slice, attempt, and parent revision; records status, result, evidence references, blockers, approvals, and a minimal next_slice. The next role reads the referenced files or knowledge keys, not pasted logs.

  • completed: the owner checks evidence and routes the next dependency.
  • blocked: name the unknown, why it matters, what was checked, and the exact question or dependency.
  • waiting_user: wait for a user decision, approval, or missing configuration.
  • failed: preserve evidence and stop or retry only within the configured budget.
Context disciplineKeep durable decisions in the ledger, canonical facts in knowledge entities, and large logs in referenced files. Put only the state required by the next slice in next_slice.
