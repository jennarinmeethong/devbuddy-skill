Task และ knowledge

ประสานงานข้าม repository โดยให้ canonical knowledge อยู่ในการควบคุมของ owner มี evidence และไม่ผูกกับ Plugin cache ของ host

Manual 0.4.6Project-qualified scopesOwner commit

Bootstrap ไม่ใช่ canonical knowledge

bootstrap scan evidence จาก manifest และ path ให้ review ก่อน ขอ Knowledge Impact Approval แล้วค่อย promote fact ที่ถาวรเป็น typed entity โดย bootstrap จะเขียนเฉพาะ labelled observation และไม่คิด policy, entity หรือ decision ให้เอง

Scan หนึ่ง project 
python3 .devbuddy/tools/bootstrap_knowledge.py \
  --devbuddy-root .devbuddy \
  --project-id fe --dry-run

สร้าง workspace task

Task เดียวข้าม FE และ BE 
python3 .devbuddy/tools/task_memory.py init \
  --devbuddy-root .devbuddy \
  --project-id fe --project-id be \
  --task-id checkout-001

ledger เก็บ revision sequence เดียวใต้ .devbuddy/tasks/ Plugin ทำหน้าที่ route คำสั่งของ host แต่ ledger และ knowledge เป็น state ของ workspace

ใช้ project-qualified scope

Reserve และ validate 
python3 .devbuddy/tools/task_memory.py reserve \
  --devbuddy-root .devbuddy --project-id fe --project-id be \
  --task-id checkout-001 --scope fe:src/checkout \
  --actor developer --expected-revision 0
python3 .devbuddy/tools/task_memory.py check-scope \
  --devbuddy-root .devbuddy --project-id fe --project-id be \
  --task-id checkout-001 --write-scope fe:src/checkout \
  --changed fe:src/checkout/cart.ts

scope ที่ไม่มี project ID จะถูก reject และ change ใต้ be: รับภายใต้ reservation ของ fe: ไม่ได้

Owner commit protocol

  1. reserve project-qualified scope
  2. dispatch specialist ด้วย read path, write scope, model, effort และ exit condition ที่อนุมัติแล้ว
  3. validate changed path และ JSON slice record
  4. commit owner revision ด้วย expected parent revision
  5. release reservation และตรวจ knowledge health

specialist ห้ามเขียน .devbuddy/ โดยตรงแม้ source scope จะได้รับอนุมัติ

Analysis และ slice record

Read-only analysis 
python3 .devbuddy/tools/task_memory.py analyze \
  --devbuddy-root .devbuddy --project-id fe \
  --task-id checkout-001

สร้าง JSON slice record ตอนถึง role boundary, checkpoint สำคัญ หรือ blocker ให้ next_slice มีเฉพาะ state ที่ slice ถัดไปต้องใช้และอ้างไฟล์/key แทนการคัดลอก log

Workflow ข้าม host

  1. ผู้ใช้เรียก host Plugin/profile ที่ติดตั้งไว้อย่าง explicit
  2. Orchestrator resolve settings, project, task ledger, risk, approval และ role graph ที่เล็กที่สุด
  3. owner เลือก model/effort ที่อนุมัติ reserve write scope และ dispatch package ที่มีขอบเขต
  4. owner ตรวจ evidence กับ record แล้ว route หรือหยุด dependency ถัดไป
  5. ถ้าขาด approval, tool ใช้ไม่ได้, revision เก่า, conflict หรือไม่แน่ใจ ให้เป็น blocked หรือ waiting_user
  6. ปิดงานเมื่อมี evidence, independent check ตาม risk, approval, knowledge declaration และ policy compliance

Specialist ทำงานอย่างไร

Actorความรับผิดชอบห้ามทำ
Orchestrator / ownerเลือก graph, ตรวจ gate, reserve scope, เลือก model/effort, route record และ commit canonical knowledge ที่อนุมัติแล้วทำ implementation แทน specialist หรือแทน specialist ที่หายไปแบบเงียบ ๆ
Specialist subagentทำ role slice เดียวใน scope ที่กำหนด เก็บ evidence และคืน JSON slice recordเขียน .devbuddy/, ขยาย scope, สร้าง artifact ที่ไม่อยู่ในรายการ, เปลี่ยน policy หรือเดา fact

Record flow

JSON slice record เป็นผลลัพธ์ระหว่าง agent เพียงรูปแบบเดียว ระบุ task, slice, attempt และ parent revision พร้อม status, result, evidence, blocker, approval และ next_slice ที่สั้น

  • completed — owner ตรวจ evidence แล้ว route dependency ต่อไป
  • blocked — ระบุ unknown, เหตุผล, สิ่งที่ตรวจ และคำถามที่ต้องการ
  • waiting_user — รอ decision, approval หรือ configuration
  • failed — เก็บ evidence และ retry เฉพาะใน budget ที่ settings อนุญาต
