Database packages are profile components

Database core and engine adapters remain in the release; they are selected into a workspace composition rather than installed as separate host UI Plugins.

Why an adapter may appear to be missing

Codex, Claude Code, and OpenCode show their native host adapter after installation. Packages such as devbuddy-database-core, devbuddy-database-mariadb, and devbuddy-database-sqlserver are not separate host UI entries. They are resolved by a data profile, written to .devbuddy/packages.json, and materialized only for the database instance the workspace explicitly selects.

Resolve and materialize

Preview first. Applying a profile records its composition but does not create credentials or execute a query. Materializing then creates one self-contained, read-only runtime for the named database instance.

python3 scripts/profile_resolver.py profiles/data-mariadb.yaml --platform codex
python3 scripts/profile_resolver.py profiles/data-mariadb.yaml --platform codex --devbuddy-root <workspace>/.devbuddy --apply
python3 scripts/materialize_database_adapter.py --devbuddy-root <workspace>/.devbuddy --database-id billing --engine mariadb
python3 scripts/materialize_database_adapter.py --devbuddy-root <workspace>/.devbuddy --database-id billing --engine mariadb --apply
python3 scripts/register_database_adapter.py --devbuddy-root <workspace>/.devbuddy --database-id billing --engine mariadb
python3 scripts/register_database_adapter.py --devbuddy-root <workspace>/.devbuddy --database-id billing --engine mariadb --apply

Registering is also dry-run first and adds the database registry only after materialization. Configure the local ignored secret file yourself, use a least-privilege read-only principal, and retain target-specific Tier 2 approval.
