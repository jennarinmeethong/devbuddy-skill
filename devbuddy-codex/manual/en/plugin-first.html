Plugin-first distribution

Install one host-native Plugin or profile. The portable core is bundled as a dependency; users do not install a second standalone core skill.

The portable policy remains in devbuddy-core. Optional capabilities, including database access, are selected through a profile and must pass their package manifest and approval gates.

Claude Code: marketplace lifecycle

The repository marketplace catalog is .claude-plugin/marketplace.json. Validate the package, add the marketplace and Plugin in the same scope, verify discovery, refresh the session, and invoke the namespaced command. Use user for a local-user installation; use project or local only when that is the intended boundary.

Install and verify 
claude plugin validate plugin/devbuddy-claude-code
claude plugin marketplace add . --scope user
claude plugin marketplace list
claude plugin install devbuddy-claude-code@devbuddy --scope user --yes
claude plugin list --json
# in Claude Code
/reload-plugins
/devbuddy-claude-code:devbuddy <task>

Plugin skills are namespaced by Claude Code. The unnamespaced /devbuddy command belongs only to the legacy standalone compatibility path.

Codex: Plugin and profile lifecycle

Codex installs a Plugin from a configured marketplace snapshot. This repository includes a marketplace catalog at .agents/plugins/marketplace.json; add its root and install devbuddy-codex@devbuddy. For another marketplace, use its root and the name shown by its list command.

Discover, install, resolve, and invoke 
codex plugin marketplace list --json
codex plugin marketplace add . --json
codex plugin list --available --json
codex plugin add devbuddy-codex@devbuddy --json
codex plugin list --json
python3 scripts/profile_resolver.py profiles/codex.yaml --platform codex --dry-run
python3 scripts/profile_resolver.py profiles/codex.yaml --platform codex --apply --devbuddy-root <workspace>/.devbuddy
# start a new Codex thread
$devbuddy <task>

The Codex adapter carries explicit approved model and reasoning_effort values for each specialist dispatch. If the host cannot transport both values, the task stops as waiting_user.

Update, disable, and roll back

Claude Code lifecycle 
claude plugin marketplace update devbuddy
claude plugin update devbuddy-claude-code@devbuddy
claude plugin list --json
# in Claude Code
/reload-plugins
claude plugin uninstall devbuddy-claude-code@devbuddy --keep-data

For this local repository marketplace, update the Plugin cachebuster, then re-add the package. A Git marketplace must be upgraded by its own marketplace name before re-adding:

# local repository marketplace
codex plugin add devbuddy-codex@devbuddy --json
codex plugin list --json
# Git marketplace only
codex plugin marketplace upgrade <marketplace>
codex plugin remove devbuddy-codex@devbuddy

Use codex plugin marketplace remove devbuddy only when no Plugin still uses that source. Start a new thread after changes. Rollback means returning to an approved package/profile version; workspace state under .devbuddy/ is not package data.

Legacy standalone compatibility

DevBuddy 1.x keeps the old installers as migration-aware shims. They report the Plugin path by default, never remove a host file, and refuse unknown-file conflicts. Use them only to inspect or explicitly preserve an existing standalone installation:

Read-only reports 
python3 devbuddy-claude/scripts/install_claude_adapter.py --migration-report
python3 devbuddy-codex/scripts/install_codex_adapter.py --migration-report

After a successful Plugin migration, remove the old standalone skill through the host configuration UI or a reviewed, reversible backup. Do not delete .devbuddy/, task ledgers, canonical knowledge, or local secrets.

Ownership and safety boundaries

  • Package artifacts own host skills, generated agents, references, schemas, templates, and delivery metadata.
  • .devbuddy/ owns workspace settings, task ledgers, tools, observations, and canonical knowledge.
  • Secrets stay in local secret files referenced by committed templates; credentials and project state never enter a Plugin artifact.
  • Database execution is Tier 2 and Plugin-owned. It requires the core package, a selected engine adapter, a manifest, a read-only principal, and target-specific approval.
  • Every install, update, migration, and removal starts with a dry-run or discovery check and stops on unknown conflicts.

Release and host verification

For repository changes, run source-preservation, package-drift, manual-conformance, secret-exclusion, and release validation checks. For a live Claude host, validate the manifest, install from the intended marketplace, run claude plugin list --json, refresh, and perform one read-only namespaced invocation. For Codex, confirm both codex plugin marketplace list --json and codex plugin list --json, then open a fresh thread.
