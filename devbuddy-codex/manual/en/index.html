Codex adapter · overview

Software delivery with a clear control plane.

Invoke DevBuddy explicitly with $devbuddy. The Orchestrator manages state, dependencies, approvals, locks, model/effort selection, and evidence; specialist roles perform the substantive work.

Start with the installer dry run, create project settings, validate, then dispatch.

Quick start

  1. Preview installation with python3 scripts/install_codex_adapter.py.
  2. Create <project-root>/.devbuddy/settings.yaml with user-approved model and effort allowlists.
  3. Validate the skill and project settings before the first dispatch.
  4. Run $devbuddy <task>; the Orchestrator selects the role graph.
python3 scripts/install_codex_adapter.py
python3 scripts/validate_skill_metadata.py .
python3 scripts/check_adapter_conformance.py
python3 -m unittest discover tests -v
$devbuddy <task>

What Codex does differently

ConcernCodex behaviour
RoleOne role profile per canonical role; role and effort stay independent.
ModelPassed per dispatch through the approved project allowlist.
EffortPassed per dispatch as reasoning_effort or the platform's documented equivalent.
VerificationThe handoff must report the model/effort pair; otherwise the slice is unverified.

Memory that stays understandable

The default project root is <project-root>/.devbuddy/. It contains settings.yaml, KnowledgeBase.md, the other core memory files, typed knowledge folders, and task ledgers. Use python3 scripts/bootstrap_knowledge.py --project-root <project-root> --dry-run to prepare a reviewable repository inventory; use --apply only after review. It writes only Context.md and KnowledgeBase.md, never overwrites non-empty existing files, and never invents typed canonical entities. An external memory_root is used directly.
